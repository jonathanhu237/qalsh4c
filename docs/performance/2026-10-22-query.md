# Further query optimization experiments — 2026-10-22

**No performance change is retained from this round.** The tested candidates
did not establish a robust whole-run benefit across representative default runs. Production search,
construction, numerical kernels, and storage formats remain identical to
`507d00a`, following [the first optimization round](2026-10-22-runtime.md).
This commit adds regression coverage, benchmark support, and the evidence
below. It does not claim a new speedup or that further optimization is impossible.

## Method and acceptance

All experiments run on Centaurus with GCC 15.2.0, native Release flags
`-O3 -DNDEBUG -march=native -g`, OpenMP enabled, and CUDA disabled. Hardware,
input preparation, fixed seeds, and approximation ratio 2 match the first
report. The frozen `507d00a` executable has SHA-256
`4ae3dfc9939d302b1cbaeb1c2405185cd6ff2a12b75ef4e2767cac4e0c4929bb`.
Each case alternates baseline and candidate processes after one warmup per
executable. Times below are medians of whole-process wall time.

The default automatic-sampling cases omit `-n`; existing defaults select 32
samples for both inputs. `cold` regenerates weights, including index building.
OS caches are warm; `cold` does not mean flushing filesystem caches.
`OMP_PROC_BIND=false` prevents worker threads inheriting single-core affinity.

| Input | A points | B points | Dimensions |
|---|---:|---:|---:|
| GMM128 | 4,000 | 20,000 | 128 |
| MNIST | 3,000 | 66,900 | 784 |

Other projects started computation during early screens. Those results are
[segregated as exploratory evidence](2026-10-22-query/exploratory/) and are
not used to substantiate the final timing tables. At the user's request,
subsequent comparisons waited for a quiet server interval. The guard samples
Linux process CPU counters once per second, excludes its command's descendant
processes, waits 20 consecutive seconds at no more than 0.5 external CPU cores,
and rejects two consecutive samples above that threshold. Its logs accompany
each accepted screen. This detects sustained competition, not every short
external process or memory/I/O disturbance. Interrupted screens are retained
as partial, rejected evidence, without completed manifests.

Every completed end-to-end timing run verifies identical weight-file hashes. Displayed
single-thread estimates must match exactly; multithreaded estimates allow
relative tolerance `2e-6` for OpenMP reduction order. This compares the CLI's
displayed estimates, not an unexposed internal bit pattern. CSV line endings
are normalized to LF with parsed fields unchanged. Perf text logs omit trailing
whitespace. Input hashes, executable
hashes, exact commands, and individual repetitions accompany each CSV.

## Candidates

A fresh default-auto GMM128 L2 single-thread profile attributed 63.72% of
sampled cycles to hit delivery, 17.07% to in-memory scanning, 6.02% to strategy
scheduling, and 1.43% to exact distances.
[Profile](2026-10-22-query/exploratory/baseline-gmm128-auto-profile.txt),
[hardware counters](2026-10-22-query/exploratory/baseline-gmm128-auto-stat.txt).

- **Compact counters:** unsigned-byte and distinct enum-byte countdowns,
  with full-width custom/large-threshold fallback. Byte stores caused additional
  pointer reloads; avoiding that aliasing still did not produce a promising
  initial screen. The original full-width counters remain.
- **Separate ID/value arrays:** retain original sort order but let the integer
  collision loop read contiguous IDs. The initial code also introduced an extra
  taken branch in the hot loop. Separate helper functions did not fix this;
  an accepted-zero branch hint did, and the inline version was the best of
  these candidates. It still regressed MNIST in guarded comparisons below.
- **Circular FIFO:** preserve the deque's ordering, duplicates, and radius
  semantics. Its initial screen did not justify advancing the candidate.
- **Branch hint alone / single-pass scan:** the hint alone was slightly slower.
  The correctly rebuilt combination showed only marginal, variable gains; the
  scan simplification without the hint substantially regressed both inputs.
  No version from this group is retained.
- **Four-way ID-loop unrolling:** preserve sequential callbacks and tails;
  no floating-point loop flags change. It was flat on GMM and slower on
  single-thread MNIST.
- **LTO:** an unchanged-source build using CMake's
  `CMAKE_INTERPROCEDURAL_OPTIMIZATION_RELEASE=ON` passed four focused tests.
  Its exploratory screen, partly affected by competing work, provided no
  sufficient reason to change the build configuration. No LTO gain is claimed.

## Verification and retained work

The final baseline production implementation plus the new regression test
passes all **33 CTest tests**. The new test uses an independent full-width
count-up oracle. It covers thresholds 1/255/256/65536, threshold overrides,
strategy reuse, custom rules observing counts above 255, invalid IDs,
typed/erased/range dispatch, empty ranges, lengths around four-way tails,
candidate order, stop callback snapshots, and full-range hit accounting.

The tested layout candidates passed the full 35/36-test suites, including
separate-array decoding under SSE2 and the scalar fallback. Passing correctness
checks was necessary, but did not establish a performance benefit. Candidate
patches are archived as evidence and are not applied to production.

The retained load-guard helper was checked on Centaurus: its own CPU-bound
child did not count as external work, and a separate CPU-bound sibling caused
rejection with exit status 75. It terminates only its owned experiment process
group. Sustained-load checks still have the sampling limitations described above.

Logs: [final 33 tests](2026-10-22-query/final-tests.txt),
[layout candidate](2026-10-22-query/soa-hint-tests.txt),

[LTO focused checks](2026-10-22-query/lto-tests.txt),

An independent OpenSpec review recomputed the timing tables and percentages,

## Reproduction

Use a local `507d00a` source snapshot, apply a candidate locally, synchronize
one-way to Centaurus, and build there with the flags above. Preserve the frozen
baseline executable. [Candidate patches](2026-10-22-query/candidates/) are
experimental records, not recommended changes. The best layout candidate is
`soa.patch` followed by `hint-only.patch`; the single-pass candidate combines
`hint-only.patch` and `scan-single-pass.patch`. The out-of-line helper patch
applies after `soa.patch`. LTO changes only the CMake setting cited above.

Example guarded default comparison on Centaurus:

```sh
python3 scripts/benchmark_idle_guard.py --log build/load.jsonl -- \
  python3 scripts/benchmark_runtime.py \
  --before build/perf-after/qalsh4c --after build/candidate/qalsh4c \
  --dataset mnist784=build/perf-data/mnist784 \
  --dataset gmm128=build/perf-data/gmm128 \
  --threads 8 --norms 1 2 --samples 0 --modes cold \
  --repeats 5 --output build/comparison.csv
```

The construction probe is run through the same guard, with matching include
and static-library paths passed to `scripts/benchmark_index_build.py`. Its
`--help` documents the complete invocation; use `--seed 1608637542` to reproduce
this report. Unlike the runtime harness, its adjacent manifest appends `.json`
to the full CSV filename.

The existing runtime harness and new build probe require Python 3.11 or newer.
A rejected load-guard run returns 75; discard its partial timing results and
retry in a new quiet interval. Do not infer future speedups on other machines,
input sizes, or compiler versions from these negative screens.
